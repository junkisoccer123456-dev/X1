# 原文
```
若手エンジニアがレビューでよく指摘されること5選
・変数名が分かりにくい
→ 「tmp」「data」ではなく役割が分かる名前に
・メソッドが長い
→ 1つのメソッドは1つの役割に
・コメントを書きすぎ
→ コードで伝わるのが理想
・例外処理が甘い
→ エラー時の動きまで考える
・テスト不足
→ 正常系だけで安心しない
```
# 分析メモ
- **冒頭フック**：見出し1行だけ。権威づけの前置きを置かない。「よく指摘されること」という
  **他人も言われている**という表現が、自分だけではないという安心と確認欲を同時に作る。
- **権威性**：明示しない。指摘する側の目線で書かれていること自体が権威になっている。
- **興味維持**：左右の2段構造。左で「自分かも」と刺し、右で解決を渡す。1項目で完結するので
  どこから読んでも成立する。
- **情報の順番**：変数名→メソッド→コメント→例外→テストと、**コードの表層から設計の深層へ**降りる。
- **比較方法**：NG→対策の対。対策は理由を書かずに動作だけ。
- **オチ・締め**：なし。5つ目の対策で終わる。締めがないぶん、チェックリストとして保存される。
- **CTA**：なし。
- **改行**：項目間に空行なし。5項目が1ブロックで、画面上で1つの表のように見える。
- **文章量**：全体170字前後。右は1行（15〜25字）。
- **文体**：左は体言止め・状態。右は「〜に」「〜まで考える」で言い切る。です・ます調を使わない。
- **絵文字**：なし。記号は ・ と → のみ。
