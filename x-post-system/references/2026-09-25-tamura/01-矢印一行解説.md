# 参考投稿①②｜矢印一行解説型（2件は同じ骨格）

## 原文（ポスト①：評価コメント版）

```
エンジニア採用してますが、
面接で「触ってます」と言われて安心する技術5選

・Git → コンフリクト解消まで話せると強い
・SQL → JOINと索引を語れる人は少ない
・Docker → 環境差分の言い訳が消える
・シェルスクリプト → 手作業を減らせる証明
・HTTP/TCPの基礎 → 障害の切り分けが速い

派手な技術名より、この5つのほうが刺さります
```

## 原文（ポスト②：定義版）

```
エンジニア採用してますが、
面接で説明できないと地味に痛い用語5選

・冪等性 
→ 何回実行しても結果が変わらない性質
・CI/CD 
→ テストとデプロイを自動で回す仕組み
・IaC 
→ サーバ構成をコードで管理する考え方
・コンテナ 
→ アプリを実行環境ごと箱詰めして動かす技術
・Kubernetes 
→ その箱を大量に指揮する現場監督

知っているだけで評価はされないですが、説明できないと理解が浅く見えてしまう、、、
```

# 分析メモ

## 1. 冒頭フック・権威性
- 1行目が「エンジニア採用してますが、」の一言だけ。長い自己紹介をしない。
- 2行目で「〇〇5選」と中身を予告する。1行目と2行目で読むかどうかが決まる設計。
- 権威性は立場のみ。年数も人数も出していない。出さなくても成立している。

## 2. 問題提起
- ①は問題提起なし。いきなり価値の提示に入る。
- ②は見出しの中に問題提起が埋め込まれている（「説明できないと地味に痛い」）。
  「痛い」「安心する」という感情語を見出しに1語入れるのが共通点。

## 3. 興味維持の仕掛け
- 項目が5つだけ。読み切れる量に抑えている。網羅より厳選。
- 矢印の右側が一行。ここが長いと読まれない。
- ①は「項目 → 評価コメント」、②は「用語 →（改行）定義」。
  ②は改行を挟むことで、定義パートが独立して読める。用語集としての保存性が上がる。

## 4. 具体例の出し方
- ①の矢印の中身は「その技術が話せると、採用側から何がどう見えるか」。
  技術の説明ではなく、評価の翻訳になっている。ここが他のまとめ投稿との差。
- ②の矢印の中身は噛み砕いた言い換え。とくにKubernetesを「箱を大量に指揮する現場監督」と
  比喩にしているのが効いている。正確さより伝わりやすさを優先している。

## 5. オチ
- ①「派手な技術名より、この5つのほうが刺さります」＝逆張りの断定で締める。
- ②「知っているだけで評価はされないですが、説明できないと理解が浅く見えてしまう、、、」
  ＝両側から挟む締め。褒めすぎず、脅しすぎない。
- どちらも1行。CTAは本文に入れていない。

## 6. 文体・見た目
- 本文は約120〜200字。②のほうが改行が多いぶん縦に長い。
- 絵文字なし。記号は ・ と → のみ。
- ②の末尾「、、、」が口語のトーンを作っている。
