# 使用した構文：n選＋リプ個別深掘り型（参考投稿②／新規作成）

【〇〇❺選】の見出し → 誰向けかを1行 → ❶〜❺を「項目名＋1〜2行の価値説明」で一覧化 →
価値を一度下げる（「〇〇は△△の代わりにはならないです」）→「が〜としては〇〇を一段押し上げます↓↓」で切る →
【リプ❶〜❺】同じ項目名で再登場し、「概要 → 採用側として正直に言うと → 面接でどう効くか」で統一

既存の `moura-list-yajirushi.md` バリエーションC（回答例リプ連載型）は本文のリストに解説を付けないため、
本文で一覧化し、同じ項目をリプで深掘りし直すこの型は新規構文として作成しました。

※資格の名称・試験区分・形式（実技かどうか）は事実のみ記載し、合格率などの数字は使っていません。

投稿01｜書類で目に留まる職務経歴書の武器❺選
━━━━━━━━━━━━━━━━━━
【経験者こそ書いて損しない職務経歴書の武器❺選】

エンジニアとして数年やってきた人が、書類の通過率を一段上げるならこれかと。

❶改善の前後が数字で書かれている一行
何をしたかより、どう良くしたかが伝わる。これだけで読む順番が変わる。

❷障害対応で自分が何を判断したか
手を動かした話は多いですが、判断の話は少ないです。希少性が出る。

❸技術選定の理由と、選ばなかった候補
「選べる人」だと示せる。候補を書くだけで一段深く見える。
❹チーム内で自分が引き受けていた役割
肩書きがなくても「回せる人」として読める。

❺引き継ぎ・ドキュメント化でチームに残したもの
自分が抜けたあとも残る仕事をした証明になる。

小手先の表現を変えても通過率はそこまで動かないです。が「選ぶ側が確認したいこと」を先に書いておくと、職務経歴書は一段読まれるものになります↓↓

【リプ❶】
❶改善の前後が数字で書かれている一行
「レスポンスを800msから120msに改善した」のような、前後が並んだ一行のことです。
採用側として正直に言うと、書類を開いて最初に探しているのがここなんですよね。数字が1個でもあると、その人が自分の仕事を測っていたことが分かる。面接でも「どう測ったんですか」から入れるので、深掘りの入口になりやすい一行です。

【リプ❷】
❷障害対応で自分が何を判断したか
「誰に何を聞いて、どこから切ったか」を書く項目です。復旧の手順ではなく判断の順番を書きます。
採用の現場で見ていると、障害の話を「対応しました」で終える方が本当に多いです。だからこそ切り分けの順番まで書いてあると目が留まる。実務で修羅場をくぐった人かどうかは、ここの具体度でほぼ分かります。

【リプ❸】
❸技術選定の理由と、選ばなかった候補
採用した技術だけでなく、比較した候補と落とした理由まで書く項目です。
採用側の本音を言うと、「使えます」と「選べます」の間には大きな差があるんですよね。候補が2つ以上書いてあると後者として見られやすい。面接で「今だったら何を選びますか」と聞いたときの返答にも期待が持てます。

【リプ❹】
❹チーム内で自分が引き受けていた役割
リーダーという肩書きではなく、実際に自分が持っていた持ち場のことです。見積もり、レビュー、障害の一次受け、新人の質問対応など。
採用側として、ここは肩書きより信じています。役職がなくても役割を書ける人は、入社後に自分で持ち場を作れる。マジでここは評価が変わるポイントかと。

【リプ❺】
❺引き継ぎ・ドキュメント化でチームに残したもの
自分が抜けたあとに残った成果物のことです。手順書、設計の記録、調査のログなど。
採用の視点だと、ここを書ける人は「次の人のことを考えて働く人」として読めます。レビューや設計の議論で噛み合いやすいタイプだと推測できる。長く効く一枚です。

━━━━━━━━━━━━━━━━━━
【30代エンジニアが狙って損しないポジション❺選】

実装は一通りできる状態まで来た人が、次の立ち位置を一段上げるならこれかと。

❶テックリード
実装を続けたまま決める側に回れる。プレイヤーを降りなくていい。

❷SRE
信頼性という共通言語を持てる。開発と運用の両方から声がかかる。
❸プラットフォームエンジニア
社内の開発者を顧客にする立場。規模が大きい会社ほど需要がある。

❹データ基盤側
事業の数字に直接触れる。企画側と話せる人が少ないので希少。

❺プロダクト寄りのエンジニア
仕様を決める側に回れる。「何を作らないか」を語れるようになる。

肩書きが変わるだけで年収が上がるわけではないです。が「判断の範囲が広い人」として見られる立場に移ると、選考での通り方が変わります↓↓

【リプ❶】
❶テックリード
チームの技術的な意思決定とレビューを持つ役割です。マネージャーと違い、人の評価は持たないことが多いです。
採用側として正直に言うと、この経験がある人は書類の段階で止まります。実装力があって、かつ決めた経験もある。面接で「反対意見が出たときどうしましたか」と聞きたくなる一枚です。

【リプ❷】
❷SRE
可用性やエラーバジェットを基準に、システムの信頼性を設計・運用する役割です。
採用の現場で見ていると、障害を減らした話を数字で語れる人は想像より少ないんですよね。だからここの経験があると、開発職でもインフラ職でも選択肢が広がる。転職市場での入口が2つになる立ち位置です。

【リプ❸】
❸プラットフォームエンジニア
社内の開発基盤（CI/CD、共通ライブラリ、開発環境）を作って提供する役割です。
採用側の本音を言うと、ここは「開発者の生産性を上げた」と数字で言える人が刺さります。他のエンジニアを顧客として扱えるかが見られる領域。従業員が多い会社ほど必要とされます。

【リプ❹】
❹データ基盤側
データの収集・加工・提供までを設計する役割です。SQLが書けるだけでは足りず、信頼できる数字を作る側に回ります。
採用の視点だと、事業側と話せるエンジニアはいつも足りないです。ここの経験があると、技術の面接だけでなく事業理解の面接でも強い。希少性が高い立ち位置かと。

【リプ❺】
❺プロダクト寄りのエンジニア
仕様の優先順位づけに関わり、作るものを決める側に回る役割です。
採用側として、この経験は「この機能は作らない」を根拠付きで言えるかどうかで見ています。それが言える人はマジで少ないです。30代でここを1回でも通ると、その後の選考が一気に楽になります。

投稿03｜インフラ寄りに振るときに効く資格❺選
━━━━━━━━━━━━━━━━━━
【インフラ側に振るなら取って損しない資格❺選】

アプリ側からインフラ寄りに移りたい人が、最初の説明材料を作るならこれかと。

❶AWS SAA（ソリューションアーキテクト アソシエイト）
構成を言葉で説明できるようになる。入口として一番費用対効果が高い。

❷LPIC／LinuC
コマンドの暗記ではなく、OSの仕組みを説明できる側だと示せる。

❸ネットワークスペシャリスト
IPAの高度試験。クラウドでも土台はネットワークなので長く効く。
❹CKAD
Kubernetes上でアプリを動かす側の実技試験。コンテナの実務力が伝わる。

❺情報処理安全確保支援士
インフラの構成を語るときに、セキュリティの前提から話せるようになる。

資格は実務経験の代わりにはならないです。が「アプリしか知らない人ではない」という最初の説明材料としては、書類を一段読ませるものになります↓↓

【リプ❶】
❶AWS SAA（ソリューションアーキテクト アソシエイト）
AWSの主要サービスを使って、可用性やコストを考えた構成を選べるかを問う資格です。上位のSAPより範囲は狭いです。
採用側として正直に言うと、アプリ側の方がこれを持っていると「構成の話ができる人かも」と目が留まります。面接で自社の構成図を見せたときの反応が違うので、話が早い一枚です。

【リプ❷】
❷LPIC／LinuC
Linuxの管理を体系的に問う資格です。ファイルシステム、権限、プロセス、パッケージ管理まで含みます。
採用の現場で見ていると、「Linuxは触れます」の中身が人によって全然違うんですよね。この資格があると、どこまで分かっているかの目安になる。インフラ側の面接官が安心しやすい一枚です。

【リプ❸】
❸ネットワークスペシャリスト
IPAの高度試験で、ネットワークの設計・構築・運用を問われます。クラウド前提でも土台は変わりません。
採用側の本音を言うと、ここを持っている方は障害調査の話が強いです。「どこで切れているか」を層で考えられる。クラウド移行の案件では特に頼りにされる領域かと。

【リプ❹】
❹CKAD（Certified Kubernetes Application Developer）
Kubernetes上でアプリを動かす側の実技試験です。CKAが運用側、CKADが開発側という位置づけになります。
採用側として、実技で取っている時点で手を動かしてきたんだろうなと推測しやすいです。アプリ側からインフラに寄せたい人の経歴とも噛み合うので、順番としてはここが自然です。

【リプ❺】
❺情報処理安全確保支援士
セキュリティ領域の国家資格です。設計や運用の中でリスクを語れるかを示せます。
採用の視点だと、構成の話にセキュリティの前提が入ってくる人は信頼されます。インフラに寄せるほど、権限設計や通信経路の話が増えるので。職種問わず加点になりやすい一枚です。

投稿04｜面接官が深掘りしたくなる経験❺選
━━━━━━━━━━━━━━━━━━
【面接官が深掘りしたくなる経験❺選】

面接で話が広がらないと感じている人が、持っていく材料を変えるならこれかと。

❶自分の判断で方針を変えた話
うまくいった話より、変えた話のほうが質問が続きます。

❷失敗して、そのあと仕組みを直した話
再発防止まで届いていると、一気に話が深くなる。
❸他職種と揉めて、落としどころを作った話
技術以外の調整ができる人かが分かる。ここは本当に差が出ます。

❹他の人の仕事を楽にした話
自分の成果ではなく、周りへの影響で語れる人は少ない。

❺やらないと決めた話
作らなかった判断を根拠付きで話せる人は、マジで希少です。

派手な技術の話は、面接では意外と広がらないです。が「判断が入っている話」を1つ持っていくだけで、面接の空気は変わります↓↓

【リプ❶】
❶自分の判断で方針を変えた話
途中まで進めた設計や進め方を、自分の判断で切り替えた経験のことです。
採用側として正直に言うと、ここを話せる方には質問が止まりません。何を見て変えたのか、誰に通したのか、結果どうだったのか。全部深掘りの材料になる。1つ持っているだけで面接が10分伸びます。

【リプ❷】
❷失敗して、そのあと仕組みを直した話
障害や手戻りを起こしたあと、再発しない形まで持っていった経験です。
採用の現場で見ていると、失敗談で終わってしまう方が多いんですよね。だからこそ仕組みの話まで届くと評価が変わる。反省ではなく設計の話として聞けるので、印象に残ります。

【リプ❸】
❸他職種と揉めて、落としどころを作った話
企画や営業と意見が割れたときに、どう決着させたかという経験です。
採用側の本音を言うと、技術力が同じなら最後はここで差が付きます。入社後に一番困るのが調整の場面なので。角が立たない言い方で通せる人は、どこの現場でも重宝されます。

【リプ❹】
❹他の人の仕事を楽にした話
自分の担当範囲の外で、チームの手間を減らした経験です。ビルド時間の短縮や手順の自動化など。
採用の視点だと、こういう話をする方は入社後の立ち上がりが早いです。周りを見ながら動けるので。評価の面談でも説明しやすい材料になります。

【リプ❺】
❺やらないと決めた話
作らなかった機能、返さなかった負債について、根拠を付けて決めた経験です。
採用側として、これが言える人は僕が見てきた範囲でも本当に少ないです。足し算の話は誰でもできるんですよね。引き算の判断ができる人は、年齢が上がってからの選考で特に強いかと。

投稿05｜バックエンドで市場価値が上がる技術領域❺選
━━━━━━━━━━━━━━━━━━
【バックエンドで触って損しない技術領域❺選】

言語は書けるようになった人が、次の市場価値を一段上げるならこれかと。

❶データベースの設計とクエリ改善
言語が変わっても持ち越せる。ここが強い人はどこでも通ります。

❷非同期処理とキュー
失敗したときにどうするかを設計できる人は少ない。希少性が出る。
❸認証・認可の設計
触りたがる人が少ないのに、どのサービスにも必要。穴場です。

❹監視と可観測性
「落ちてから気づく」から抜け出せる。障害の話が語れるようになる。

❺既存システムの切り出し
モノリスを少しずつ分ける経験。これができる人は本当に足りてません。

新しい言語を1つ増やしても、評価はそこまで動かないです。が「言語が変わっても残る領域」を1つ深くしておくと、選考での説明が強くなります↓↓

【リプ❶】
❶データベースの設計とクエリ改善
正規化の判断、索引の設計、スロークエリの改善までを含む領域です。言語やフレームワークが変わっても持ち越せます。
採用側として正直に言うと、ここが強い方は職種を問わず欲しいです。パフォーマンスの話で地に足のついた回答が返ってくる期待値が上がる。長く効く領域かと。

【リプ❷】
❷非同期処理とキュー
処理をキューに逃がし、失敗したときの再試行や重複を設計する領域です。冪等性の話が中心になります。
採用の現場で見ていると、「キューを使いました」と「設計しました」の差が大きいんですよね。失敗時の挙動まで語れる方は少ないので、ここは面接で一気に深掘りしたくなる領域です。

【リプ❸】
❸認証・認可の設計
ログインの実装ではなく、誰が何をできるかを設計する領域です。権限の設計は後から直すのが一番しんどい部分です。
採用側の本音を言うと、ここを避けずにやってきた方は信頼できます。地味なのに事故が重い領域なので。穴場なのに評価されやすい、珍しい分野です。

【リプ❹】
❹監視と可観測性
ログ、メトリクス、トレースを設計して、問題を先に見つけられる状態を作る領域です。
採用の視点だと、ここを触っている方は障害の話が具体的です。「どこを見て気づいたか」から話せる。運用を知っているエンジニアとして、書類の段階で差が出ます。

【リプ❺】
❺既存システムの切り出し
大きくなったシステムから機能を少しずつ分けていく経験です。新規開発より難しく、経験者が本当に足りていません。
採用側として、ここを語れる人には必ず時間を取ります。何から切ったか、どう移行したか、止めずにやれたか。全部が判断の話になるので、評価が上がりやすい領域かと。

投稿06｜社内で取っておくと転職で効く役割❺選
━━━━━━━━━━━━━━━━━━
【転職前に引き受けて損しない社内の役割❺選】

今の会社で動きながら市場価値を上げたい人が、手を挙げるならこれかと。

❶新しく入った人のオンボーディング担当
教える側に回ると、自分の理解の穴が全部見えます。

❷障害対応の一次受け
判断の経験が一番速く積める持ち場。経歴書で強い一行になります。
❸見積もりとスケジュールの作成
「実装できる人」から「案件を回せる人」への入口です。

❹採用の技術面接への同席
選ぶ側の目線が分かるので、自分の選考が一気に有利になります。

❺外部ベンダーとの窓口
技術と条件の両方を扱う経験。社内だけでは積めない部分です。
