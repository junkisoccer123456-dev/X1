# 構文名：言葉の定義段階型

## この構文が読まれやすい理由
- 誰もが使っている一言（「実装、終わりました」）をカギ括弧で置くだけで、**読者が自分の口癖を思い出す**。
  入口のハードルがゼロなのに、自分ごとになる。
- 「人によって意味が全然違うんですよね」の1行で、**自分はどの意味で使っていたかを確認したくなる**。
  この時点で最後まで読む理由ができている。
- 段階が「・上記に加えて」で**入れ子**になっているので、下に行くほど要求が増えることが一読で分かる。
  番号を振らなくても階段に見えるのが、この型の設計の核。
- 最後に「面接では、この言葉がどの段階を指すかで評価がガラッと変わる」と落とすので、
  **読者が自分の職務経歴書・面接の言い方を直したくなる**。行動に直結するぶん保存される。

## 基本構造
```
①現場でよく使われる一言をカギ括弧で置く（句点で切る）
 ↓
②「この一言、人によって意味が全然違うんですよね」
 ↓
③・段階1（いちばん浅い定義。1行）
 ↓
④・上記に加えて、段階2（1行）
 ↓
⑤・上記を満たしたうえで、段階3（1行）
 ↓
⑥・上記を満たしたうえで、段階4（1行）
 ↓
⑦・上記を満たしたうえで、段階5（1行）
 ↓
⑧面接・評価の話に落とす（「"〇〇"がどの段階を指すかで、評価はガラッと変わります」）
```

## 抽象テンプレート
```
「【現場でよく使われる一言】」。
この一言、人によって意味が全然違うんですよね。

・【段階1：いちばん浅い定義】

・上記に加えて、【段階2】

・上記を満たしたうえで、【段階3】

・上記を満たしたうえで、【段階4】

・上記を満たしたうえで、【段階5】

面接でも「【その言葉を含む自己PRのセリフ】」の"【言葉】"がどの段階を指すかで、
評価はガラッと変わります。
```

## 相性の良いテーマ
- 定義が人によってブレる業界用語・現場用語（リリース、運用、設計、マネジメント、改善、レビュー）
- 段階が**包含関係**で並べられるテーマ（下の段階が上の段階を含む）
- 面接・評価の場面に落とせるテーマ

## 相性の悪いテーマ
- 段階が並列なテーマ（入れ子にならないと「・上記に加えて」が嘘になる）
- 段階が3つ以下のテーマ（階段に見えない。4〜5段がちょうどいい）
- 言葉がニッチすぎるテーマ（読者が自分の口癖として認識できない）

## 文体・見た目のメモ
- 文章量：200〜300字
- 段階は1行ずつ。**各段階のあいだに空行を入れる**（階段の段差に見せる）
- 「・上記に加えて」「・上記を満たしたうえで」の言い回しをあえて繰り返す。揃えるほど効く
- 段階は下に行くほど「本人の外に出る」順（手元 → チーム → 本番 → 関係者）にすると自然に重くなる
- 絵文字なし。CTAも入れない（最後の1文で締める）

## ⚠️ 運用上の注意
段階の中身は技術的に正しい順序でなければならない。
現場を知らないと「・上記に加えて」の包含関係が崩れるので、
**実際の開発フロー・業務フローの順番から外れていないか確認する**こと。
